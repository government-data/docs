  1. Traefik

    A reverse proxy: it receives connections, terminates TLS and routes each request to the service behind it by its path. It can require and check client certificates.

    Why here One door for people and machines alike: routes come from each module's manifest, so a module added or removed changes its route and nothing else; it authenticates, and leaves what a person may do to the module.

    To run it
    Ports :443 for people; the internal entry point for machines
  2. In this platform · the installation's only entry point, for people and for machines, and the gate in front of the lake
  3. in every installationThe web entry point, HTTPS on :443: the application, the guide and every module's screens, each under its own pathMain server · Traefik · edge; cable browser → Traefik :443 on the main server; people's browser
  4. in every installationThe internal entry point: the installation's machines and modules, each with a certificate of its CAMain server · Traefik · edge; cable Trino coordinator ↔ Trino worker; cable main server → lake gate · the core's lake adapter, Loki and Mimir
  5. in every installationForward authentication: for a module with no sign-in of its own, it asks the core for a valid session firstMain server · Traefik · edge; Main server · Quality Data · API
  6. in every installationRoutes come from the modules' manifests, written by the agent when a module is addedMain server · Traefik · edge; Main server · qd agent
  7. in every installationThe lake's gate: lets in only connections with a certificate of the installationLake server · Lake gate · Traefik; cable Trino worker → lake gate · S3 and Iceberg REST; cable main server → lake gate · the core's lake adapter, Loki and Mimir
  8. optionalThe replica's gate, at the other siteLake replica · gate · Traefik; cable lake server → lake replica at another site (optional)
  1. Quality Data

    The platform's core and its package: the data quality application, plus sign-in, permissions, audit, settings and the installation's machines.

    Why here Every module asks one place who a person is and what they may do, and one place writes every SQL statement a job runs.

    Rust and SolidJS

    Rust is a compiled language with memory safety checked by the compiler; SolidJS is a library for the browser that updates only what changed.

    Why here Single fast binaries for the server and the agents, and a light web app served as static files.

    To run it
    Needs PostgreSQL, Dolt and the lake
  2. In this platform · the core every module needs: its server in Rust and its web app in SolidJS

  1. OpenID Connect

    The standard sign-in protocol built on OAuth 2.0: an application sends the person to the provider and gets back who they are.

    Why here People sign in once and enter every module with that session; machines and jobs get short-lived tokens instead of long-lived passwords.

    To run it
    Needs the core; optionally the organisation's directory or an external provider

  1. Mutual TLS

    In mutual TLS both ends of a connection show a certificate and check the other's. A certificate authority signs them.

    Why here Services trust a certificate, not where a connection comes from; the installation's own CA is shared with no one, and agents renew its certificates without hands.

    To run it
    Needs a time source on every machine: certificates last about a day
  2. In this platform · every server and service proves who it is with a short-lived certificate of the installation's own authority
  3. in every installationThe CA, made when the installation is installed, kept as files beside the coreMain server · CA · certificates

  1. The orchestrator

    The platform's operator of jobs, and the job runners it hands them to.

    Why here Running a cut is split in three roles, each doing one thing: the core writes and signs, the operator schedules and tracks, the job runners send and report. It runs Trino's coordinator, so it knows when Trino may restart.

    To run it
    Needs the core and Trino
  2. In this platform · the operator fires schedules and tracks every job; it also runs and manages the Trino coordinator
  3. in every installationThe operator fires the schedules, keeps each job's state and retries with backoffMain server · Operator

  8. in every installationThey report only names, counts, snapshot ids and any failed stage back to the coreMain server · Job runner 1; Main server · Job runner 2; Main server · Quality Data · API
  1. Trino

    Why here One engine for every job and every dashboard: it reads the organisation's databases and the lake, and it grows by adding workers.

    To run it
    Memory about 13 GB for Trino on a worker machine, to start*
    Disk a spill disk of its own
